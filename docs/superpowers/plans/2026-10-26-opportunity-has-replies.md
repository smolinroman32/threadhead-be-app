# Replies Flag on Opportunities Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Store `has_replies` from `keyword_search` on each opportunity and show it as a chip on the card.

**Architecture:** The flag flows unchanged from the Threads adapter through `FoundPost` into `saveScored`, is
stored as a nullable column, and comes back through the entity, mapper and response DTO. The frontend reads it
from `IOpportunityDto` and renders one chip.

**Tech Stack:** NestJS 12, Prisma 7, Vitest (`threadhead-be`); Next.js, Tailwind (`threadhead-fe`).

**Spec:** `threadhead-be/docs/specs/opportunity-has-replies.md`

## Global Constraints

- No comments in code.
- `null` means unknown and is never turned into `false`.
- The migration is generated by the user from `threadhead-be` with
  `npx prisma migrate dev --config prisma7.config.ts --name opportunity_has_replies`; the agent never writes or
  applies it.
- Chip copy: `No replies yet` for `false`, `Has replies` for `true`, nothing for `null`.
- Both repos have unrelated uncommitted changes: stage only the files a task names.
- Commit messages: Conventional Commits, imperative, no trailing period, body says why, ending with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

- A post found again by a later run keeps its first `hasReplies`: `saveScored` must keep `skipDuplicates` and add
  no update path.
- `saveRescored` must not touch `hasReplies`.
- Rows from before the migration have `null` and show no chip.
- The frontend deployed before the backend gets `hasReplies` as `undefined`: the card checks `=== true` and
  `=== false`, so no chip and no crash.
- Threads sending `has_replies: null` maps to `null`, same as a missing field.
