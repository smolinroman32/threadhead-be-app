# Spec: replies flag on opportunities

Status: agreed after grilling. Open questions: none.

Builds on [discovery.md](discovery.md) (`keyword_search`, `Opportunity`) and the opportunity card in
`threadhead-fe/src/entities/opportunity/ui/opportunity-card.tsx`. The frontend change is small and lives in this
spec too.

## Goal

The opportunity card tells the user whether the post already had replies when discovery found it. A post with
replies has a live conversation, so it gets the accent chip.

## Live API findings (2026-10-26)

Checked with a connected account token (`threads_basic`, `threads_keyword_search`, `threads_read_replies`) on
posts of other users:

- `keyword_search` returns `has_replies`; we already request it.
- `GET /{id}?fields=like_count|reply_count|replies_count|repost_count|quote_count|views`: code 100,
  `nonexisting field`.
- `GET /{id}/insights`: 403, code 10. `GET /profile_lookup`: 403, code 10.
- `GET /{id}/replies` works for other users' posts, pages of 25 with `paging`, fields `id`, `timestamp`,
  `username`; no like counts and no total.

So the official API gives no counters, followers or display names for other users' posts. Only `has_replies` is
free.

## Decisions

| Topic             | Decision                                                                                     |
| ----------------- | -------------------------------------------------------------------------------------------- |
| Source            | `has_replies` from `keyword_search` only; no `/replies` calls                                |
| Freshness         | a snapshot taken when the post is first saved; never updated                                 |
| Unknown value     | `null` end to end; a missing `has_replies` is not `false`                                     |
| Existing rows     | `null`                                                                                       |
| Card              | one chip: `true` is "Has replies" (accent), `false` is "No replies yet" (neutral), `null` none |
| Counters, followers, display name from the design | dropped, no source                                           |
| Filter or sort    | none, the snapshot goes stale                                                                |

Out of scope, each its own later spec: refreshing the flag on a schedule, deleting old opportunities, counters and
followers (FR-12, FR-13), a "no replies" filter.

## Data

The migration is generated by `npx prisma migrate dev --config prisma7.config.ts --name opportunity_has_replies`,
run by the user from `threadhead-be`, never written by hand. It only adds a nullable column, so it cannot fail on existing rows.

```prisma
model Opportunity {
  hasReplies Boolean?
}
```

## Contract

`OpportunityResponseDto` and every route that returns opportunities gain one field:

```ts
hasReplies: boolean | null;
```

## Changes by layer

- `SocialPost.hasReplies` in the social-accounts port becomes `boolean | null`. `ThreadsAccountApi.searchPosts`
  maps a missing `has_replies` to `null`.
- `FoundPost` gains `hasReplies: boolean | null`; `DiscoveryWorkRepository.saveScored` writes it. A post that is
  already stored keeps its first value (`skipDuplicates`).
- `OpportunityEntity`, `OpportunityMapper`, `OpportunityResponseDto`, `DiscoveryResponseMapper.opportunity` carry
  `hasReplies`.
- Frontend: `IOpportunityDto.hasReplies: boolean | null`; the chip goes first in the card footer list. Accent
  styling is the one the strong match badge uses (`bg-chart-1/10 text-chart-1`); neutral is the existing chip
  style.

## Acceptance checks

1. A search result without `has_replies` maps to `hasReplies: null`; `true` and `false` pass through.
2. A discovery run hands `saveScored` posts with their `hasReplies`.
3. `GET /opportunity-feeds/:id/opportunities` returns `hasReplies` as `true`, `false` or `null` as stored.
4. The card shows "No replies yet" for `false`, "Has replies" for `true` and no chip for `null`.
