# Spec: opportunity discovery

Status: agreed after grilling. Open questions: none.

Builds on `opportunity-feeds` (feeds, onboarding completion) and `social-accounts` (OAuth, `getAccessToken`).
Product context: [docs/prd.md](../prd.md) sections 7 to 14 and [opportunity-discovery.md](../../../docs/opportunity-discovery.md).

## Goal

For a feed bound to a connected Threads account, find fresh public Threads posts through `keyword_search`,
drop the obvious misses cheaply, score the rest for relevance with an LLM, and keep them as `Opportunity`
records the user can review, save or dismiss.

Out of scope, each its own later spec: metrics and top replies of other users' posts (FR-12, FR-13, need
`getPostSnapshot` after the M0 checks), reply drafts and publishing, `TOP` search, pagination of search
results, a cron for discovery runs, a language detector, rescoring on a model or prompt change, user deletion,
the frontend (`threadhead-fe/docs/specs`).

## Decisions

| Topic                  | Decision                                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------- |
| Search token           | the user's own token; discovery needs a connected Threads account (PRD FR-1 changes)                      |
| Feed and account       | a feed belongs to one `SocialAccount`; `socialAccountId` is set once while `null`, then immutable         |
| Trigger                | manual `POST`, plus automatic after feed creation, onboarding completion, a criteria change and a resume  |
| Manual cooldown        | a manual `POST` is refused for 6 hours after the last run that did not fail; automatic runs are not blocked |
| Execution              | BullMQ worker on the existing Redis; `DiscoveryRun` in Postgres is the source of truth                    |
| Retries                | only `DiscoveryRun.attempt` counts; BullMQ `attempts: 1`, `maxStalledCount: 0`                            |
| Status delivery        | polling a run by id; no SSE                                                                               |
| Search queries         | `includeTerms` as `KEYWORD` plus up to `min(6, 10 - terms)` LLM `PHRASE` queries                          |
| Search call            | `search_type=RECENT`, `search_mode=KEYWORD`, `since = now - freshnessHours`, `limit=100`, one page         |
| Score                  | `relevanceScore`, LLM relevance `0..100`; `minScore` and freshness apply on read, for `new` only          |
| Stored posts           | every LLM-scored post; prefilter drops are not stored                                                     |
| Rescoring              | `scoringVersion` on the feed and on each opportunity                                                      |
| Exclusions             | `excludedTerm` on the opportunity; hidden from `new`, kept and marked in `saved`                          |
| LLM                    | `LlmPort` with `completeJson`, adapter `OpenAiLlmClient` over the existing `HttpClientPort`               |
| Language               | English only; the scoring prompt returns `0` with reason `not English`                                    |
| Disconnect             | soft: `disconnectedAt` set, token erased, the row and its id survive a reconnect                          |

## Data

The migration is generated by `prisma migrate dev`, run by the user in their terminal (it is blocked for the
agent), never written by hand. `SearchQuery`, `Opportunity` and
`OpportunitySearchQuery` hold no rows yet, so their changes are free. Existing feeds get
`socialAccountId = null` and `scoringVersion = 1`. Existing accounts keep their tokens.

```prisma
enum OpportunityStatus {
  NEW
  SAVED
  DISMISSED
  REPLIED
}

enum DiscoveryRunStatus {
  QUEUED
  RUNNING
  SUCCEEDED
  FAILED
}

enum SearchAccess {
  OK
  NARROWED
  UNKNOWN
}

model OpportunityFeed {
  socialAccountId String?        @db.Uuid
  socialAccount   SocialAccount? @relation(fields: [socialAccountId], references: [id], onDelete: Restrict)
  scoringVersion  Int            @default(1)
  discoveryRuns   DiscoveryRun[]
}

model Opportunity {
  relevanceScore Int
  status         OpportunityStatus
  scoringVersion Int
  excludedTerm   String?
}

model DiscoveryRun {
  id                String             @id @default(uuid()) @db.Uuid
  opportunityFeedId String             @db.Uuid
  opportunityFeed   OpportunityFeed    @relation(fields: [opportunityFeedId], references: [id], onDelete: Cascade)
  status            DiscoveryRunStatus
  scoringVersion    Int?
  attempt           Int                @default(0)
  heartbeatAt       DateTime?
  notBefore         DateTime?
  error             String?
  stats             Json               @default("{}")
  createdAt         DateTime           @default(now())
  startedAt         DateTime?
  finishedAt        DateTime?
}

model SocialAccount {
  accessTokenEncrypted  String?
  tokenExpiresAt        DateTime?
  disconnectedAt        DateTime?
  searchAccess          SearchAccess?
  searchAccessCheckedAt DateTime?
  opportunityFeeds      OpportunityFeed[]
}
```

Only the changed fields are shown. The nullable `accessTokenEncrypted` and `tokenExpiresAt` land with the soft
disconnect task, together with the code that handles a missing token, in a migration of their own. `Opportunity.score` is renamed to `relevanceScore`; `status` moves from
`String` to the enum.

`onDelete: Restrict` blocks a physical delete of an account that still has feeds. Disconnect is soft, so the
only path that removes account rows is `DELETE /users/me` (`prisma.user.delete`), which cascades to both the
accounts and the feeds. A rolled-back probe on Postgres showed that this cascade passes with a bound feed while
a direct account delete is refused, but the order of cascade actions is not a documented guarantee, so check 21
pins it with an end-to-end run. If it ever fails, the user deletion deletes the feeds first in one transaction.

## Contract

All routes need the access cookie. The user id comes from the token. A feed, run, opportunity or account of
another user, or a missing one, is 404.

| Method and path                                     | Result                                                        |
| --------------------------------------------------- | ------------------------------------------------------------- |
| `POST /opportunity-feeds/:id/discovery-runs`        | 202 run: the feed's existing `queued` run or a new one         |
| `GET /opportunity-feeds/:id/discovery-runs/:runId`  | 200 run                                                       |
| `GET /opportunity-feeds/:id/discovery-runs/latest`  | 200 the newest run by `createdAt`; 404 if the feed never ran   |
| `GET /opportunity-feeds/:id/opportunities?status=`  | 200 `{ items, hasMore }`; `status` defaults to `new`          |
| `PATCH /opportunities/:id`                          | 200 opportunity; body `{ status: "new" \| "saved" \| "dismissed" }` |
| `POST /social-accounts/:id/search-access-check`     | 200 `{ searchAccess, checkedAt }`; ignores the TTL            |

`POST /discovery-runs` errors, all 409: `account_required` (no account and none can be bound),
`reconnect_required` (account inactive or disconnected), `feed_paused`, and `DiscoveryCooldownError` while the
cooldown below is active.

### Manual cooldown

The newest run of the feed that is not `failed`, automatic or manual, starts a cooldown of
`MANUAL_RUN_COOLDOWN_MS` from its `createdAt`. Only the manual `POST` is refused; the automatic triggers (feed
creation, onboarding completion, a criteria change, a resume) go around it and, being runs, start the cooldown
themselves. A failed run starts none, so a user can retry after a failure. Every run response carries
`nextRunAt`: the end of the cooldown, or `null` when it has passed or no run counts. The `POST` response is
computed from the run it returns, the `GET` responses from the newest run that is not `failed`.

Run in a response:

```json
{
  "id": "uuid", "status": "queued", "error": null,
  "stats": {}, "createdAt": "iso", "startedAt": null, "finishedAt": null, "nextRunAt": "iso"
}
```

Opportunity in a response:

```json
{
  "id": "uuid", "externalPostId": "string", "authorUsername": "string", "text": "string",
  "permalink": "url", "publishedAt": "iso", "relevanceScore": 82, "reason": "string",
  "status": "new", "stale": false, "excludedTerm": null, "matchedQueries": ["string"]
}
```

`stale` is `opportunity.scoringVersion < feed.scoringVersion`. Status values are lower case in JSON.

### Reading opportunities

| `status`                          | Filters                                                                                     |
| --------------------------------- | ------------------------------------------------------------------------------------------- |
| `new`                             | `relevanceScore >= minScore`, `publishedAt` within `freshnessHours`, `excludedTerm` is null, author is not the feed account |
| `saved`, `dismissed`, `replied`   | none                                                                                        |

Order: `relevanceScore DESC`, `publishedAt DESC`, `id`. The query takes `OPPORTUNITY_LIST_LIMIT + 1` rows;
`hasMore` is whether the extra row came back.

### Status transitions

| From \ to   | `new`               | `saved`  | `dismissed` |
| ----------- | ------------------- | -------- | ----------- |
| `new`       | 200, no change      | yes      | yes         |
| `saved`     | yes                 | 200, no change | yes   |
| `dismissed` | yes                 | yes      | 200, no change |
| `replied`   | 409 `opportunity_replied` | 409 | 409        |

`replied` is set only by the future reply flow.

### Feed contract changes

- `socialAccountId` is in the feed response and accepted by `POST` and `PATCH`. The account must belong to the
  user, else 404. Changing a non-null value is 409 `feed_account_locked`; sending the same value is a no-op.
- `POST` without `socialAccountId`, and onboarding completion, bind the user's only active account when there
  is exactly one.
- A `PATCH` that really changes `intent`, `targetAudience`, `includeTerms` or `excludeTerms` runs, in the
  feed's locked transaction: `scoringVersion + 1`, every `SearchQuery` of the feed to `isActive = false`,
  `excludedTerm` recomputed for every `new` and `saved` opportunity of the feed, and a queued run (coalesced, see
  below) when the feed is active. Text is compared after `trim`, terms as case-insensitive sets after
  `normalizeTerms`, so a reorder is not a change.
- `isActive: false -> true` queues a run when the feed has a `queued` run or stale opportunities.

## Social accounts changes

- `disconnect` sets `disconnectedAt = now`, `isActive = false`, `accessTokenEncrypted = null`,
  `tokenExpiresAt = null`. The row stays. `GET /social-accounts` hides disconnected accounts.
- `connect` finds the account by `(provider, providerAccountId)` including disconnected rows, updates it in
  place and clears `disconnectedAt`. The id is kept, so feed bindings survive.
- `getAccessToken` on a disconnected account throws `SocialAccountReconnectRequiredError`.
- `isActive = false` without `disconnectedAt` keeps its current meaning: refresh failed, reconnect required.
- Facade additions: `searchPosts(accountId, { query, since, limit })` and `checkSearchAccess(accountId)`.
  `SocialAccountApiPort` gains a keyword search, implemented in `ThreadsAccountApi`.
- After a successful `connect` the search access check runs without blocking the redirect. Its failure only
  leaves `searchAccess = UNKNOWN`.

### Search access check

The control query runs with the account's token.

| Control result                         | `searchAccess` |
| -------------------------------------- | -------------- |
| at least one post by another author    | `OK`           |
| only the account's own posts           | `NARROWED`     |
| empty                                  | `UNKNOWN`      |
| network error or 5xx                   | `UNKNOWN`      |
| explicit missing-permission error      | `NARROWED`     |

## Discovery run

### Queue and coalescing

- At most one `queued` and one `running` run per feed. Creating or reusing the `queued` run happens under the
  feed row lock (`SELECT ... FOR UPDATE`, as `updateLocked` already does).
- `POST`, or an automatic trigger, with a `queued` run present returns that run. With only a `running` run
  present it creates a `queued` run and does not add a job: the running run adds it in its `finally`.
- Jobs carry `{ runId }` and no fixed `jobId`; every enqueue is a new job, with `removeOnComplete` and
  `removeOnFail`. A duplicate job is harmless because of the claim below.
- A job is added after the creating transaction commits. If adding fails, the run stays `queued` and the
  reconciler picks it up.

### Claim and fencing

The worker claims the run in one locked transaction. The claim succeeds when the feed is active, no other run
of the feed is `running` with a fresh heartbeat, and either `status = queued` and `notBefore <= now` (or null),
or `status = running` and `heartbeatAt < now - HEARTBEAT_STALE_MS`. It sets `status = running`,
`attempt = attempt + 1`, `heartbeatAt = now`, `startedAt` if null, and `scoringVersion = feed.scoringVersion`.
A failed claim ends the job with no work. A claim that finds the feed paused sets the run back to `queued`.

Every later write of the worker runs in a transaction that starts with
`UPDATE "DiscoveryRun" SET "heartbeatAt" = now() WHERE id = $runId AND attempt = $attempt AND status = 'RUNNING'`.
Zero rows means a newer executor owns the run: the transaction rolls back and the worker exits silently.
Opportunity updates also carry `WHERE "scoringVersion" <= $runScoringVersion`.

### Safe points

Before each Threads call and each LLM batch the worker writes a heartbeat and re-reads the account and the
feed. A disconnected or inactive account ends the run `failed` with `account_disconnected` or
`reconnect_required`. A paused feed sets the run back to `queued`.

### Steps

1. Claim.
2. Account: active and not disconnected, token from `getAccessToken`.
3. Access: `NARROWED` checked less than `SEARCH_ACCESS_TTL_MS` ago fails the run with
   `search_permission_narrowed` before any search. An older `NARROWED` runs the check first and continues only
   on `OK`.
4. Rescoring: opportunities with `scoringVersion < run.scoringVersion`, status `new` or `saved`,
   `excludedTerm` null, published within `freshnessHours`. Stored text, no Threads call, batches as in step 8.
5. Queries: when the feed has no active `KEYWORD` queries, create one per `includeTerm`. When it has no active
   `PHRASE` queries and `MAX_SEARCH_QUERIES - terms > 0`, ask the LLM for phrases. A failed generation keeps the
   keyword queries, adds the warning `query_generation_failed`, and the next run retries.
6. Search each active query. A result of exactly `SEARCH_LIMIT` posts adds the query to `truncatedQueries`.
   `matchedPosts` grows by the posts the query returned.
7. Suspicious result: more than zero posts in total, all by the account. Run the access check regardless of the
   TTL. `NARROWED` fails the run with `search_permission_narrowed`; `OK` continues; `UNKNOWN` continues with
   the warning `permission_check_inconclusive`. Empty results are a normal `succeeded`.
8. Prefilter, then scoring in sequential batches of `SCORING_BATCH_SIZE`. Each batch inserts its opportunities
   (`status = NEW`, `scoringVersion = run.scoringVersion`) and their `OpportunitySearchQuery` links in one
   fenced transaction. `relevantPosts` grows for each linked query of a post scored at `>= feed.minScore`.
9. Finish: `succeeded` (with `partial_scoring` when some posts stayed unscored) or `failed`, `finishedAt`, and
   in `finally` the feed's `queued` run is enqueued when the feed is active.

### Prefilter

In order, each drop counted in `stats.dropped.<reason>`:

1. Duplicate `id` across the run's queries: one candidate keeping every matching query id.
2. Already an opportunity of the feed, found by one `findMany` over the candidate ids: no LLM call, only new
   links through `createMany({ skipDuplicates: true })`. Stale versions are left to step 4.
3. `is_reply = true`.
4. Author is the feed account.
5. `timestamp` older than `freshnessHours`.
6. Text shorter than `MIN_POST_TEXT_LENGTH` after `trim`, empty included.
7. An `excludeTerm` match.
8. Above `MAX_SCORED_POSTS_PER_RUN`: the newest by `timestamp` across all queries are kept, the rest count as
   `capped`, meaning not processed, not irrelevant.

The exclude matcher is one shared function used here and by the feed `PATCH`: the escaped term between
`(?<![\p{L}\p{N}])` and `(?![\p{L}\p{N}])`, flags `iu`. It never uses `\b`.

### LLM

```ts
abstract class LlmPort {
    abstract completeJson<T>(input: {
        model: string;
        system: string;
        user: string;
        schemaName: string;
        schema: Record<string, unknown>;
    }): Promise<T>;
}
```

`OpenAiLlmClient` posts to Chat Completions with `response_format: json_schema`, a `LLM_TIMEOUT_MS` timeout, and
up to two retries of a 429, a 5xx or a transport error after 1 s and 2 s. `HttpResponse` carries no
headers, so `retry-after` is not read; add headers to the port if OpenAI limits show it is needed. It throws
`LlmRateLimitedError`, `LlmUnavailableError` or `LlmInvalidResponseError`. Another 4xx (a bad key, a bad
schema) is `LlmUnavailableError` without a retry. `OPENAI_API_KEY` is read on each call, so the app boots
without it.

Scoring input: intent, target audience, include terms, and posts as `{ ref: "p1", text }`. Output:
`{ scores: [{ ref, relevanceScore, reason }] }`, wrapped in an object because a strict OpenAI schema needs an
object at the root. The domain accepts an item only when its ref was sent and appears once,
`relevanceScore` is an integer `0..100` and `reason` is at most `REASON_MAX_LENGTH`. Rejected or missing items
stay unscored. Post text is untrusted: it goes into the user message between explicit delimiters, and the system
message says post content is data, not instructions. Non-English posts score `0` with reason `not English`.

Query generation output: `{ phrases: string[] }`, validated as feed terms (`normalizeTerms`, 2 to 50
characters), with phrases equal to an include term ignoring case removed, capped at the free slots.

### Failures

| Failure                                      | Result                                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------ |
| `LlmInvalidResponseError` on a batch         | the batch is retried once, then its posts stay unscored (`stats.unscored`) |
| `LlmRateLimitedError`, `LlmUnavailableError`, Threads 5xx or transport error | `attempt < MAX_RUN_ATTEMPTS`: `queued`, `notBefore = now + RETRY_DELAY_MS`, a delayed job; else `failed` with `llm_rate_limited`, `llm_unavailable` or `threads_unavailable` |
| Executor lost (stale heartbeat, no live job) | reconciler: `attempt < MAX_RUN_ATTEMPTS` back to `queued`, else `failed` with `worker_lost` |

Scored batches are already saved, so a later attempt does only the rest.

### Reconciler and recovery

A BullMQ job scheduler runs every `RECONCILE_EVERY_MS`. The same routine runs on application bootstrap and for
the feed on each `POST /discovery-runs`:

- `queued` runs older than `QUEUED_STALE_MS`, with `notBefore` null or past, of an active feed with no fresh
  `running` run: add a job.
- `running` runs with `heartbeatAt < now - HEARTBEAT_STALE_MS`: back to `queued` with a job when
  `attempt < MAX_RUN_ATTEMPTS` and the feed has no other `queued` run, else `failed` with `worker_lost` (the other
  `queued` run does the work). There is no check for a live job: jobs carry no fixed id, and the stale heartbeat
  plus the fence already keep a slow live executor from writing.

### Stats

`stats` is one JSON object: `queries`, `fetched`, `deduped`, `dropped` (by reason), `scored`, `rescored`,
`unscored`, `truncatedQueries` (query strings), `searchAccessCheck` (`ok`, `narrowed`, `unknown`, `skipped`),
`warnings` (strings). The worker writes it at each safe point, so polling shows progress.

## Module

Discovery lives inside `opportunity-feeds`. The feed is the aggregate root of `SearchQuery`, `Opportunity` and
`DiscoveryRun`, and a criteria `PATCH` must bump the version, deactivate queries, recompute exclusions and queue
a run in one transaction, which a separate module could only do through a cycle.

```
src/shared/llm/
  llm.module.ts            LlmPort -> OpenAiLlmClient
  ports/llm.port.ts
  adapters/openai-llm.client.ts
  errors/
src/shared/queue/
  queue.module.ts          BullMQ connection from REDIS_URL, closed on shutdown
src/shared/terms/
  match-excluded-term.ts
src/modules/opportunity-feeds/
  domain/
    entities/              opportunity, discovery run, search query
    discovery/             prefilter, scoring validation, phrase validation, criteria diff
    ports/                 opportunity, discovery run repositories, discovery queue port
  application/use-cases/   request run, run discovery, reconcile runs, list opportunities, change status
  infrastructure/
    repositories/
    queue/                 worker, scheduler, queue adapter
  presentation/            discovery runs and opportunities controllers, DTOs
src/modules/social-accounts/
  application/use-cases/   check search access, search posts
```

`OpportunityFeedsModule` imports `SocialAccountsModule` (facade only), `LlmModule` and `QueueModule`.
`social-accounts` does not import feeds. The worker uses `bullmq` directly through `QueueModule`, not
`@nestjs/bullmq`. BullMQ 6 makes `ioredis` an optional peer and cannot load it from native ESM, so
`QueueFactory` passes its own `ioredis` client (`maxRetriesPerRequest: null`) and closes workers, queues and
the client on shutdown.

## Architecture check

- Layers: domain code (prefilter, matcher, validation, criteria diff) has no framework imports; use cases
  depend on ports; repositories return entities through mappers.
- Errors: every new error is a `DomainError` with a kind; the 409s use `conflict`.
- Deviation 1: discovery is part of `opportunity-feeds`, not its own module (reason above).
- Deviation 2: binding the only account happens when a feed is created and on onboarding completion, not when
  an account is connected. `social-accounts` cannot reach feeds without a module cycle. A feed left unbound
  is bound on its next `POST /discovery-runs` when the user has exactly one active account.

## Acceptance checks

Runs and queue

1. `POST /discovery-runs` returns 202 `queued` and adds a job with `{ runId }`.
2. Past the cooldown, a second `POST` while `queued` returns the same run id. While `running` it creates a
   `queued` run that gets no job until the running one finishes, then gets one.
3. A failed job add leaves the run `queued`; the reconciler, the bootstrap and the next `POST` each add a job
   and the run finishes.
4. A `running` run with a stale heartbeat and no live job is re-queued and finishes with `attempt = 2`; at
   `attempt = 2` it ends `failed` with `worker_lost`.
5. An executor with an outdated `attempt` that writes a batch rolls back and changes nothing.
6. Two jobs for one `queued` run: one does the work, the other ends with no work.
7. 409 `account_required`, `reconnect_required`, `feed_paused`; another user's feed or run is 404;
   `GET /:runId` and `GET /latest` return the right runs.

Search

8. Include terms become `KEYWORD` queries and the LLM adds `min(6, 10 - terms)` `PHRASE` queries; a failed
   generation keeps the keywords, warns, and the next run generates the phrases.
9. The search call uses `RECENT`, `KEYWORD`, `since`, `limit=100`; exactly 100 results lands the query in
   `truncatedQueries`; empty results end `succeeded`.
10. All results by the account trigger the check: `OK` continues, `NARROWED` fails with
    `search_permission_narrowed`, `UNKNOWN` succeeds with `permission_check_inconclusive`.
11. `NARROWED` younger than 24 hours fails without a search call; older runs the check first;
    `POST /search-access-check` updates the status and ignores the TTL. Each row of the control result table.

Prefilter

12. Every drop reason is counted; a post found by two queries is one opportunity with two links; an existing
    opportunity gets new links and no LLM call.
13. The matcher matches `c++` and `café` as whole terms and not inside a longer word; the cap keeps the 300
    newest across all queries and counts the rest as `capped`.

Scoring

14. Batches of 20 run in order and each is saved before the next; a missing, repeated or invalid ref stays
    unscored; an invalid response is retried once.
15. A rate limit re-queues the run with `notBefore`; the second attempt scores only the rest; a second failure
    ends `failed` with `llm_rate_limited` and keeps the partial results.

Versions and exclusions

16. A `PATCH` with the same values, reordered or in another case, keeps the version and queues nothing; a real
    change of `intent` bumps the version, deactivates the queries and queues one coalesced run.
17. A new exclude term hides matching `new` opportunities at once and marks matching `saved` ones with
    `excludedTerm`; removing the term clears it; scores and reasons stay.
18. Stale `new` and `saved` opportunities show `stale: true` and are rescored by the next run; `dismissed` and
    `replied` are not; an older run cannot overwrite a newer version.

Pause and account

19. On a paused feed a `queued` run gets no job; a job already taken returns the run to `queued`; resuming adds
    a job and the run finishes.
20. `disconnect` erases the token and hides the account; a `running` run ends `failed` with
    `account_disconnected` at the next safe point; reconnecting the same profile keeps the account id and the
    feed binding.
21. `socialAccountId` is set once while `null`; replacing it is 409 `feed_account_locked`; a feed created by a
    user with one account is bound to it; deleting an account row that has feeds fails;
    `DELETE /users/me` of a user with a bound feed succeeds and removes both.

Reading

22. `new` applies `minScore`, freshness, `excludedTerm` and the author filter; other statuses apply none;
    order and `hasMore` with 101 rows; every cell of the transition table, `replied` is 409.

23. Within 6 hours of a run that is not `failed`, a manual `POST` is 409 `DiscoveryCooldownError` and adds no job;
    after a `failed` run, or after 6 hours, it is 202. `nextRunAt` is the end of the cooldown on `POST` and `GET`,
    and `null` once it passed or when only failed runs exist. Automatic triggers are not blocked.
