# Spec: opportunity metrics in the reply panel

Status: agreed after grilling. Open questions: none.

Builds on [opportunity-has-replies.md](opportunity-has-replies.md), which found that the official API gives no
counters for other users' posts, and on [opportunity-reply.md](opportunity-reply.md) (the reply panel). Covers part
of FR-12 from the PRD.

## Goal

When the user opens the reply panel for an opportunity, the panel shows the post's likes, replies and reposts and
the author's display name. Display only: the metrics never filter, rank or trigger extra searches.

## Source findings (2026-10-30)

Checked from a local machine on 6 opportunities from the 2026-10-30 run:

- `GET <permalink>` with the Googlebot user agent returns 200 with server-rendered HTML, no login wall, about
  0.6 MB, 0.7 to 1.1 s per page. No 429 at one request per second.
- The post sits in a `<script type="application/json">` block under `__bbox.result.data.media`. The old
  `thread_items[].post` path that `raw/threads-content-research-agent` uses is gone.
- The page `pk` (`4019459459307031389`) is not the API id (`18474160897139027`). The page `code` equals the
  shortcode in our `permalink`.
- The same page carries replies, quoted posts and self-thread posts with their own `code` and `like_count`.
- Fields: `like_count`; `text_post_app_info.direct_reply_count`, `repost_count`, `quote_count`; `user.full_name`.
  `view_count` is absent.
- Not checked from a server IP.

## Decisions

| Topic           | Decision                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------- |
| Trigger         | opening `OpportunityReplyPanel`; never during discovery, never for cards in the list           |
| Fields          | likes, replies, reposts, author display name; no quotes, views, followers or verified flag     |
| Unknown value   | `null` per field; a present `0` is `0`                                                         |
| Storage         | nullable columns on `Opportunity` plus `metricsFetchedAt`                                      |
| Freshness       | stored metrics younger than 1 hour are returned without a request to Threads                   |
| Failure         | one attempt, 5 s timeout, no retries; return what is stored, log a warning                     |
| After a failure | `metricsFetchedAt` stays; the next panel open tries again; no cooldown                         |
| Rate limit      | none; load is bounded by panel opens                                                           |
| Kill switch     | `THREADS_POST_METRICS_ENABLED`, default `false`; off means no requests, stored values returned |
| Post lookup     | recursive search for an object with `code === shortcode` and a `like_count` key, any path      |
| List DTO        | unchanged; metrics come only from the metrics endpoint                                         |
| `hasReplies`    | unchanged, stays the discovery snapshot                                                        |

Out of scope, each its own later spec: top replies (FR-13), velocity, "room to stand out", author responsiveness,
metrics on list cards, ranking by metrics, followers, quotes.

## Data

The migration is generated by `npx prisma migrate dev --config prisma7.config.ts --name opportunity_metrics`, run by
the user from `threadhead-be`, never written by hand. It only adds nullable columns, so it cannot fail on existing
rows; they start with all metrics `null`.

```prisma
model Opportunity {
  likeCount         Int?
  replyCount        Int?
  repostCount       Int?
  authorDisplayName String?
  metricsFetchedAt  DateTime?
}
```

## Contract

`POST /opportunities/:id/metrics`, same ownership rules as `POST /opportunities/:id/reply`. No body.

```ts
{
    likeCount: number | null;
    replyCount: number | null;
    repostCount: number | null;
    authorDisplayName: string | null;
    fetchedAt: string | null; // ISO; null when metrics were never fetched
}
```

Always 200 for an opportunity the user owns, including when Threads fails or the switch is off.

## Changes by layer

- Env: `THREADS_POST_METRICS_ENABLED` in `shared/env`, boolean, default `false`; added to `.env.example` and the
  README table.
- Social accounts: adapter `infrastructure/threads/threads-post-page.ts` on the shared `HttpClient`, behind a
  domain port. It fetches the permalink with the Googlebot user agent and a 5 s timeout, reads every
  `<script type="application/json">` block, and finds the post by the shortcode taken from the permalink. A login
  wall, an error page, a non-200 status or no matching post is an error. Use case `GetPostMetrics` and facade
  method `SocialAccountsService.getPostMetrics(permalink)`, the first facade method with no account or token.
- Opportunity feeds: use case `RefreshOpportunityMetrics`.
    - Switch off: return stored values.
    - `metricsFetchedAt` younger than 1 hour: return stored values.
    - Otherwise call `getPostMetrics`. Success: save all five columns and return them. Error: log a warning with the
      reason and return stored values.
- `OpportunityEntity`, the repository and the mapper carry the new fields. `OpportunityResponseDto` does not.
- Frontend `entities/opportunity`: the metrics model, mapper and one mutation hook for the endpoint.
- Frontend `OpportunityReplyPanel`:
    - Calls the hook when it opens.
    - Header: display name on the first line, `@username` below. Without a display name, `@username` only. The time
      leaves the header.
    - Under the post text one line, always shown: `Posted 42 minutes ago`, then `· 1.2K likes · 23 replies · 31 reposts`
      with `null` fields skipped. Numbers use `Intl.NumberFormat` with `notation: 'compact'`. A skeleton replaces the
      metrics while the request runs. When `fetchedAt` is older than 1 hour, a muted `updated 3h ago` follows.
    - "Why it's worth a reply": the `reason` paragraph becomes a row of icon, label and value. One row for now:
      `#` icon, "Topic fit", `reason`.
- The opportunity card in the list does not change.

## Acceptance checks

1. The parser returns likes, replies, reposts and display name of the post whose `code` matches, from a synthetic
   page that also holds a reply and a quoted post with other codes.
2. A missing metric field parses to `null`; a `0` stays `0`.
3. The adapter errors on a login wall page, an error page and a page with no matching post.
4. With the switch off, the use case makes no request and returns stored values.
5. With metrics younger than 1 hour, the use case makes no request and returns stored values.
6. With stale metrics and a successful fetch, the use case saves and returns the new values with a new
   `fetchedAt`.
7. With stale metrics and a failed fetch, the use case returns stored values, keeps `metricsFetchedAt` and logs a
   warning.
8. `POST /opportunities/:id/metrics` returns 404 for another user's opportunity.
9. The panel shows the display name, the posted line with metrics, the skeleton while loading, `updated Nh ago` for
   stale values and only `Posted …` when all metrics are `null`.
10. Before the switch is turned on for a server: from that server, `curl -A '<Googlebot UA>'` 3 to 5 permalinks of
    recent opportunities. Each returns 200, no login wall, and the HTML holds `like_count`.

Fixtures are synthetic HTML in the same shape, no real pages: they hold other people's posts and go stale with the
next markup change.

## Risks

- Automated collection with a Googlebot user agent breaks Meta's terms. The scraper is anonymous and never uses the
  users' OAuth tokens, so their accounts and the app review are not involved. Turning the switch on in production is
  the owner's decision.
- Meta can block or login-wall a server IP. Check 10 covers it before launch; warnings in the logs cover it after.
- The markup changes regularly. The lookup by `code` and `like_count` does not depend on the JSON path.
